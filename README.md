# Assert SQL

Declarative SQL assertions powered by [SQM](https://github.com/icher-g/sqm).
Test SQL structure without executing queries or relying on fragile string comparisons.

## Direction

- Lightweight Java library with no assertion-framework dependency.
- SQM provides SQL parsing, inspection, rendering, and optional catalog validation.
- Immutable, reusable expectations describe the checks to perform.
- Terminal operations evaluate expectations: `matches`, `evaluate`, and `assertMatches`.
- Assertion failures use standard `AssertionError`; SQL is never executed.

The core contracts are available in `io.assertsql`:

- `Expect`: immutable declarations with `evaluate`, `matches`, and `assertMatches` terminals.
- `Expect.Builder`: mutable declaration API; `build()` produces an immutable `Expect`.
- `Check`: custom checks receiving SQM's `Statement` directly.
- `Match`: immutable results created with `Match.of(...)`, including readable diagnostics.
- `Mismatch`: a diagnostic code, statement path, and message.
- `ParameterizedSql`: SQL text and optional caller-supplied named, anonymous, and ordinal bindings.
- `CollectionExpect`: counts and matching rules over an ordered list of supplied SQL statements.

Java reserves `assert`, so the throwing terminal operation is named `assertMatches`.

## Runnable application examples

[Application examples](assert-sql-examples/README.md) show how to assert SQL
generated by jOOQ and by an application-owned builder. They cover projections,

```shell
mvn -B -ntp -pl assert-sql-examples -am verify
```

These test-only examples also run in the normal CI build. They add no runtime
dependencies to Assert SQL core and are not published as library artifacts.

## Declare and evaluate expectations

```java
import io.assertsql.Expect;
import static io.sqm.core.dialect.SqlDialectId.POSTGRESQL;

var usersQuery = Expect.sql(POSTGRESQL)
    .as("active users query")
    .select()
    .table("users")
    .noSelectStar()
    .structurallyEquals("SELECT id FROM users WHERE active = true")
    .build();

// Declaration and build() do not parse SQL or invoke checks.
// The built expectation can be reused across calls and threads.
usersQuery.assertMatches("select id from users where active = TRUE;");

boolean matches = usersQuery.matches("SELECT * FROM users");
var result = usersQuery.evaluate("SELECT id FROM orders");
System.out.println(result.describe());
```

`Expect.sql(...)` supports SQM's `ANSI`, `POSTGRESQL`, `MYSQL`, `SQLSERVER`, and
`ORACLE` dialect identifiers. Builders collect requirements by mutating themselves;
their implementation class is private. `build()` requires at least one check and
copies the declaration into an immutable expectation. A description alone does
not count as a check. Further builder changes do not affect earlier snapshots.
Builders are not thread-safe. A trailing semicolon is allowed; statement sequences
are rejected. Core checks inspect SQL structure; catalog validation is available
through the optional module below. SQL is never executed.

All three terminal methods use the same evaluation path. `matches` returns a
boolean, `evaluate` returns a `Match`, and `assertMatches` throws a standard
`AssertionError` with the diagnostics on failure. Results can also be used with
another assertion framework, for example JUnit's
`assertTrue(result.matches(), result::describe)`.

## Compare the complete query structure

Use `structurallyEquals(...)` when the entire query is the contract. Declare the
expected SQL directly; whitespace, ordinary comments, keyword case, and an optional
trailing semicolon do not affect the comparison.

```java
var userPage = Expect.sql(POSTGRESQL)
    .as("user page structure")
    .structurallyEquals("""
        SELECT id, name
        FROM users
        WHERE active = true
        ORDER BY id
        LIMIT 20 OFFSET 40
        """)
    .build();

// The same structure with different formatting and keyword case passes.
userPage.assertMatches("select id, name from users where active = TRUE order by id limit 20 offset 40;");

// A changed page size is a structural mismatch.
var result = userPage.evaluate("SELECT id, name FROM users WHERE active = true ORDER BY id LIMIT 10 OFFSET 40");
System.out.println(result.describe());
```

Output:

```text
[user page structure] SQL did not match expectations:
- [STRUCTURE_MISMATCH] Expected SQL <LIMIT 20 OFFSET 40> but was <LIMIT 10 OFFSET 40>.
```

Calling `userPage.assertMatches(...)` with the changed query throws an
`AssertionError` containing that same diagnostic. Identifier spelling and quoting,
aliases, projection order, predicates, literals, and parameter names remain
significant. This compares parsed structure, not semantic equivalence. Use focused
checks such as `table(...)` or `leftJoinTable(...)` when other query changes should
remain acceptable.

For SQL generated by application code, see the
[complete-query showcase](assert-sql-examples/src/test/java/io/assertsql/examples/CustomBuilderExampleTest.java).

## Scope checks to a query

Use `.outer(...)` and `.cte(name, ...)` to apply checks to a particular query level.
For example, the outer query below reads `active_users`; the physical `users` table
is referenced in its CTE, and `audit` is referenced in an EXISTS subquery:

```java
var sql = """
    WITH active_users AS (
        SELECT id FROM users WHERE active = true
    )
    SELECT a.id FROM active_users a
    WHERE EXISTS (SELECT 1 FROM audit x WHERE x.user_id = a.id)
    """;

Expect.sql(POSTGRESQL)
    .outer(query -> query
        .table("active_users a")
        .column("a.id")
        .noTable("users", "audit")
    )
    .cte("active_users", query -> query
        .table("users")
        .exactProjection("id")
        .where("active = true")
    )
    .build()
    .assertMatches(sql);
```

Each callback receives an independent mutable `Expect.Builder` and runs during
declaration. Its non-empty declaration is copied when the callback returns. Do not
call `build()` inside the block; the parent builds the complete expectation.
Descriptions set with `.as(...)` inside a block label that scope's diagnostics.
Changing a retained child builder later does not change the captured block.

Actual SQL is parsed once per expectation evaluation. Scope selection and traversal
use the original SQM model, with no SQL rewriting or extra resolver. Unscoped calls
retain their existing behavior, including recursive reference searches. Custom
checks in scoped blocks receive the original selected statement, including its
nested queries and WITH definitions; built-in search boundaries do not alter it.

| Check family | Behavior inside a scope block |
| --- | --- |
| `select()` | Checks whether the selected statement is a query; a DML CTE body does not satisfy it. |
| `table`, `noTable`, `column`, `noColumn` | Search references at the selected level, including DML targets and RETURNING expressions. References in nested queries or CTE definitions do not count. CTE references are names, not expanded physical tables. |
| `join`, `noJoin`, `joinTable`, `noJoinTable` and typed join helpers | Search joins at the selected level. Complete join fragments still compare the entire join model, including its condition. |
| `noSelectStar()` | Inspects wildcard projections at this level, excluding nested queries and CTE definitions. |
| `parameter`, `noParameter`, `parameterCount`, `positionalParameterCount` | Inspect occurrences at this level, including pagination, excluding nested queries and CTE definitions. Correlated references appearing only inside a subquery remain excluded. |
| `projection`, `noProjection`, `exactProjection` | Compare complete outer SELECT items of the selected body; subqueries inside an item remain part of that comparison. Set queries use the first term's projection. |
| `where`, `noWhere` | Compare the complete outer WHERE of the selected body, including nested SQL inside that predicate. A set query has no single outer WHERE. |
| `orderBy`, `noOrderBy`, `limit`, `noLimit`, `offset`, `noOffset` | Inspect outer clauses of the selected body, preserving the existing `SQM_SCOPE_UNSUPPORTED` guard for ambiguous set-query clause ownership. |
| `structurallyEquals`, `satisfies` | Compare or inspect the complete selected statement, including nested SQL. An `outer` selection removes surrounding WITH wrappers; a `cte` selection retains the whole CTE body. |

A set-operation scope includes its member terms at the same search level, while
excluding subqueries and WITH definitions inside those terms. For INSERT, the target
and local expressions belong to the level; an INSERT's SELECT source is a nested query.
CTE bodies can be any statements supported by the selected SQM parser, including
PostgreSQL's data-modifying CTEs. These selectors do not add SQL semantic validation.

### CTE names and nesting

`.cte("active_users", ...)` searches only definitions in the current statement's
immediate WITH clause. Names are unqualified SQL identifiers; supply SQL quoting
when needed, for example `.cte("\"ActiveUsers\"", ...)`. Unquoted names compare
case-insensitively; if either name is quoted, their values must match exactly.
Aliases, schema qualifiers, and table modifiers are invalid selector inputs.

Nested and shadowed names are selected explicitly:

```java
Expect.sql(POSTGRESQL)
    .cte("report", report -> report
        .cte("inputs", inputs -> inputs.table("users"))
        .outer(query -> query.table("inputs"))
    )
    .build();
```

Here `report` must itself contain `WITH inputs AS (...)`. Its `inputs` definition is
independent of any equally named definition in the root WITH or other subqueries.
No descendant search, inherited-definition lookup, sibling-body traversal, or
SQL name-resolution/definition-order validation occurs. A recursive self-reference
remains a table reference; it is never expanded or revisited as a definition.

A missing CTE produces `SCOPE_NOT_FOUND`; multiple matching definitions produce
`SCOPE_AMBIGUOUS`. Both fail the block even when it contains only negative checks.
Invalid actual SQL still produces parse diagnostics and skips selection/checks.
Invalid selector syntax or expected fragments throw during evaluation after actual
SQL parses; missing selectors do not suppress declaration errors.

Diagnostics identify `outer query` or the CTE's name and one-based WITH definition
number. Nested blocks retain their scope chain, and underlying diagnostic paths
are relative to that selection. Rendered structural differences show the scope and
SQL fragments; model paths appear only in the structural fallback. SQM does not
retain SQL source spans on these nodes, so scope locations are not line/column offsets.
Scopes combine with AND like other checks and work inside `Expect.or(...)` alternatives.

The [jOOQ scope showcase](assert-sql-examples/src/test/java/io/assertsql/examples/JooqExampleTest.java)
demonstrates these checks on generated SQL with a CTE and a correlated EXISTS query.

### Derived tables and EXISTS subqueries

Use `.derived(alias, ...)` for a derived-table query and `.exists(...)` for an
EXISTS subquery at the current level. Each block uses the same declaration,
snapshot, and check-boundary rules as the outer/CTE blocks above:

```java
var sql = """
    SELECT page.id FROM (
        SELECT u.id FROM users u WHERE u.active = true
    ) page
    WHERE EXISTS (SELECT 1 FROM audit a WHERE a.user_id = page.id)
    """;

Expect.sql(POSTGRESQL)
    .derived("page", query -> query
        .table("users u")
        .where("u.active = true")
        .noTable("audit")
    )
    .exists(query -> query
        .table("audit a")
        .where("a.user_id = page.id")
        .column("a.user_id", "page.id")
        .noTable("users")
    )
    .build()
    .assertMatches(sql);
```

Selectors always search the current query level, even when called outside
`.outer(...)`. They do not search nested bodies, sibling bodies, or WITH definitions.
The alias must belong to a derived query in FROM/JOIN, including parser-supported
LATERAL/APPLY wrappers. A base-table alias or alias on a CTE reference does not
select a derived query. Alias parsing and matching follow the CTE identifier rules.
Two matching aliases produce `SCOPE_AMBIGUOUS`; no match produces `SCOPE_NOT_FOUND`.

`.exists(...)` requires exactly one direct EXISTS/NOT EXISTS predicate. For several
siblings, use the zero-based indexed form to select each intended body explicitly:

```java
Expect.sql(POSTGRESQL)
    .exists(0, query -> query.table("audit").noTable("orders"))
    .exists(1, query -> query.table("orders").noTable("audit"))
    .build();
```

Indices follow SQM visitor order within the current level, not SQL character
offsets. In a SELECT, projection expressions are visited before FROM/JOIN and
WHERE; predicates within each clause follow model traversal order. Set terms
follow their model order. A nested EXISTS is excluded until its containing query
is explicitly selected. Adding another sibling or moving predicates between
clauses can change the indices. The indexed form selects one body and does not
assert the total candidate count. Out-of-range indices produce `SCOPE_NOT_FOUND`;
negative indices are rejected during declaration. All selectors select one query,
so no implicit any/all quantification applies.

Both EXISTS and NOT EXISTS are eligible. This selector asserts the subquery's
contract, not the surrounding predicate's polarity or truth. Use a complete
`where(...)` expectation when that surrounding predicate is part of the contract.
Correlated columns such as `page.id` count as references in the selected subquery
where they appear; this does not resolve them to a catalog table or prove runtime
properties such as tenant isolation.

Deep nesting uses nested blocks, for example
`.derived("page", page -> page.exists(audit -> audit.table("events")))`.
Derived and EXISTS scopes can also contain `.cte(...)` and `.outer(...)` blocks.
Missing and ambiguous selection fails before any child check runs, including
negative-only blocks. Expected fragment/selector validation still happens during
preparation. Selection reuses the original parsed nodes; no SQL substring is reparsed.
Scalar and IN subqueries are not selected implicitly by these initial selectors.

Diagnostics retain the selector chain, for example
`derived table "page" / EXISTS subquery[0]`. The
[jOOQ nested-query showcase](assert-sql-examples/src/test/java/io/assertsql/examples/JooqExampleTest.java)
constructs and checks a real derived table plus correlated EXISTS query.

## Capture Hibernate SQL

The [Hibernate example](assert-sql-examples/README.md#hibernate-sql-capture) targets
Hibernate ORM **6.6.59.Final** and its public `StatementInspector` hook. Copy
[HibernateSqlCapture](assert-sql-examples/src/test/java/io/assertsql/examples/fixtures/HibernateSqlCapture.java)
into your test sources. It records SQL verbatim and returns it unchanged to Hibernate.

The runnable [HibernateExampleTest](assert-sql-examples/src/test/java/io/assertsql/examples/HibernateExampleTest.java)
creates mapped users/profiles, persists fixture data, and executes HQL against H2.
It asserts the SQL generated by Hibernate and separately checks returned rows,
including a user without a profile and an INNER JOIN regression.

With a `sessionFactory` from the included
[HibernateDatabase](assert-sql-examples/src/test/java/io/assertsql/examples/fixtures/hibernate/HibernateDatabase.java)
fixture, register a fresh capture on the session used by the operation. `ExampleUser`
maps to `users` and `tenantId` maps to `tenant_id`:

```java
import io.assertsql.Expect;
import io.assertsql.examples.fixtures.HibernateSqlCapture; // Use the package of your copied helper.
import java.util.List;
import static io.sqm.core.dialect.SqlDialectId.ANSI;
import static org.junit.jupiter.api.Assertions.assertEquals;

var capture = new HibernateSqlCapture();
try (var session = sessionFactory.withOptions().statementInspector(capture).openSession()) {
    var transaction = session.beginTransaction();
    try {
        session.createQuery("select u.id from ExampleUser u where u.tenantId in :tenantIds order by u.id", Long.class)
            .setParameterList("tenantIds", List.of(42L))
            .getResultList();
        var statements = capture.statements();
        assertEquals(1, statements.size(), "Expected one SQL statement from this operation.");
        Expect.sql(ANSI)
            .as("Hibernate tenant lookup")
            .select()
            .table("users")
            .column("tenant_id")
            .parameterCount(1)
            .positionalParameterCount(1)
            .build()
            .assertMatches(statements.getFirst());
    } finally {
        transaction.rollback();
    }
} finally {
    capture.clear();
}
```

The normal build runs these real Hibernate/H2 tests. Hibernate generates and executes
the queries; Assert SQL inspects the captured text. The fixture's SQL uses the subset
accepted by SQM's ANSI parser; choose the corresponding dialect for your application.
The hook captures JDBC placeholders such as `?`, not their bind values.

The passing example uses an `IN` predicate because SQM 0.5.0 fails to parse compact
equality such as `tenant_id=?` emitted by Hibernate. A separate real query demonstrates
that parser failure. Captured SQL is never rewritten to hide it.

Use one capture per session/test to isolate parallel tests. A factory-wide capture
must be thread-safe and needs additional coordination to separate test operations.
See the example documentation for registration choices and capture cleanup.

## Assert captured statement collections

Use `Expect.statements(dialect)` to assert an ordered `List<String>` from an
application-owned capture. This API is in core, with no additional dependencies.
It does not capture or execute SQL itself.

```java
var readBudget = Expect.statements(ANSI)
    .as("tenant lookup budget")
    .count(2)
    .selectCount(2)
    .updateCount(0)
    .build();

readBudget.assertMatches(capture.statements());
```

`count(...)` checks the exact total. `selectCount`, `insertCount`, `updateCount`,
`deleteCount`, and `mergeCount` check the exact count of their statement kind;
zero forbids that kind. Every supplied entry counts once, including duplicate SQL.
Subqueries, set-operation terms, and CTE bodies do not become separate entries.
WITH is classified by its outer body. For example, a SELECT with an UPDATE inside
a CTE is one SELECT; `updateCount(0)` checks outer statement kinds, not all possible
database side effects. The chosen SQM parser must support the SQL: SQM 0.5.0
currently rejects WITH followed by an outer INSERT or UPDATE.

Add a callback when only statements satisfying additional conditions should count:

```java
Expect.statements(ANSI)
    .selectCount(2, query -> query
        .table("users")
        .parameterCount(1)
    )
    .updateCount(0)
    .build()
    .assertMatches(statements);
```

The kind is restricted **before** the callback's checks are evaluated. A users
UPDATE cannot count toward `selectCount`, and callers need no `.select()` in the
callback. The callback above permits additional SELECTs that do not meet its
conditions; combine it with `.selectCount(2)` if those must also be excluded.

Declarations are AND-combined. Mutable builders snapshot their requirements on
`build()` and require at least one check. Filter callbacks run during declaration,
must add at least one check, and are snapshotted when they return. SQL is parsed
only at a terminal operation. Callback filters reuse the same original parsed
SQM nodes across rules, with fragments prepared before any custom check runs.
Built expectations support concurrent reuse when their custom checks are thread-safe.

For advanced cases, an existing `Expect` can match whole statements through
`matchingCount(expectation, count)`, `any(expectation)`, `all(expectation)`, and
`none(expectation)`. These methods apply exactly the supplied expectation, with
no implicit statement-kind restriction: a table expectation can match SELECTs
and DML. They accept OR-combined expectations:

```java
var users = Expect.sql(ANSI)
    .table("users")
    .build();
var audit = Expect.sql(ANSI)
    .table("audit")
    .build();

Expect.statements(ANSI)
    .all(Expect.or(users, audit))
    .build()
    .assertMatches(statements);
```

| Rule | Empty collection |
| --- | --- |
| `any(expectation)` | Fails |
| `all(expectation)` | Passes |
| `none(expectation)` | Passes |
| `matchingCount(expectation, 0)` | Passes |
| Any exact count greater than zero | Fails |

Every terminal defensively copies the input list, rejects null lists/elements,
preserves order, and parses every entry in the collection dialect first. Entries
are individual statements, not scripts to split. Any parse error fails the result
and skips all requirements, even count-only or absence rules. Valid SQL that fails
an ordinary filter is a non-match. Matching rules inspect every candidate; an
early success cannot hide a later error. Existing-Expect matchers evaluate each
original SQL string using their own configured dialect, so they can parse it again.
Their parse errors also fail the rule. Unavailable bindings or unsupported SQM
checks (`BINDINGS_UNAVAILABLE`, `SQM_SCOPE_UNSUPPORTED`, `VALIDATION_UNSUPPORTED`)
likewise cannot prove a zero count or absence. This API supplies SQL strings only,
without binding values. Configuration and unexpected custom-check exceptions
propagate unchanged instead of becoming assertion mismatches.

`evaluate`, `matches`, and `assertMatches` have the same roles as for single SQL.
Diagnostics preserve zero-based input indices, for example:

```text
- [UPDATE_COUNT_MISMATCH] collection.updateCount: Expected 0 matching UPDATE statements but found 1 at indices [1].
```

Member parsing and filter failures use paths such as `statements[1].sql[20]` or
`statements[1].statement.parameters`. The collection description is included in
throwing assertion messages.

[StatementCollectionExampleTest](assert-sql-examples/src/test/java/io/assertsql/examples/StatementCollectionExampleTest.java)
captures real Hibernate SQL, enforces an explicit two-SELECT budget, and catches
an unexpected UPDATE between the reads. Such budgets can expose additional-query
regressions in a controlled capture window. They do not diagnose N+1 behavior from
SQL text alone; the application owns the capture window and expected query budget.

## Built-in checks

- `select()` accepts queries, including WITH queries and set operations, and rejects DML.
- `table(String... names)` uses SQM's `TableRefsCollector` and filters its results
  to named `Table` nodes. This includes CTE references, joins, subqueries, CTE
  definitions, and DML targets. Aliases, derived tables, and function tables do
  not count as named tables. An unqualified name matches any schema; a qualified
  name requires the specified schema. An expected alias, such as `"Users AS u"`
  or `"Users u"`, must match the alias on that same table reference. Omitting an
  expected alias allows any alias or no alias. References are parsed during evaluation. This
  checks model references, without resolving CTEs to physical database tables.
- `column(String... names)` finds SQM `ColumnExpr` references anywhere in the
  statement, including expressions, predicates, joins, and nested queries. An
  unqualified name matches any table qualifier; a qualified name requires that
  qualifier. Identifier matching follows the same rules as table names. Projection
  aliases, wildcards, and DML target identifier lists are not column expressions.
- `join(String... joins)` matches complete join fragments using SQM model equality,
  including join type, right-side source, and condition. It searches all query
  scopes. For example, `join("LEFT JOIN orders o ON o.user_id = u.id")`.
- `where(String... predicates)` matches the complete outer WHERE predicate using
  SQM model equality. Supply predicates without the `WHERE` keyword. WITH queries
  inspect their body, and UPDATE/DELETE inspect their own WHERE. A predicate found
  only in a subquery does not match; parts of an AND/OR predicate do not match the
  complete predicate. Join and WHERE equality preserve identifier spelling.
- `noTable(...)`, `noColumn(...)`, `noJoin(...)`, and `noWhere(...)` require each
  supplied fragment to be absent, using their positive counterpart's matching
  rules. `noJoin()` forbids all joins, including nested ones. `noWhere()` requires
  no outer WHERE; WHERE clauses inside subqueries are allowed. A different outer
  WHERE satisfies `noWhere("id = 1")`, whereas `noWhere()` rejects any outer WHERE.
- `noSelectStar()` rejects both `*` and qualified wildcard projections
  in every query scope. `COUNT(*)` is allowed.
- `joinTable(String... names)` checks immediate named table sources of joins in
  all query scopes, without fixing the ON/USING condition. `innerJoinTable`,
  `leftJoinTable`, `rightJoinTable`, and `fullJoinTable` also require the join kind.
  `joinTable(JoinKind, String...)` exposes SQM's kinds directly, including STRAIGHT.
  ON and USING joins can match a kind; CROSS/NATURAL joins match the untyped
  `joinTable` check. `noJoinTable(...)` and `noJoinTable(JoinKind, ...)` forbid those
  matches. These methods use table name/schema/alias matching, not full structural
  join equality. A table only inside a joined derived query is not that join's
  immediate named source.
- `projection(String... items)` requires individual structural SELECT items in
  the outer projection; additional items and different list order are allowed.
  `noProjection(...)` forbids those items. `exactProjection(...)` requires exactly
  those items in that order, preserving duplicates. Aliases, expression structure,
  identifier spelling, and wildcards are significant. Omitting an expected alias
  does not ignore an actual alias. WITH uses its body; a set operation uses its
  first term's projection. DML has no SELECT projection for these checks.
- `orderBy(String... items)` checks the entire outer ORDER BY list in order,
  including direction, NULL ordering, expressions, and ordinals. Supply individual
  items without `ORDER BY`. Explicit ASC and omitted direction are distinct SQM
  structures. `noOrderBy()` requires no outer ordering. Neither method searches
  subqueries or window ordering.
- `limit(long)` and `offset(long)` check literal counts on the outer query.
  SQM maps LIMIT/OFFSET and OFFSET/FETCH to the same model. Ordinary SQL Server
  TOP is recognized as a limit; TOP PERCENT and WITH TIES are not fixed row limits.
  Parameterized expressions do not match literal counts. Absence differs from
  explicit zero. `noLimit()` requires no limit specification (including TOP or
  LIMIT ALL); `noOffset()` requires no offset. Negative expected counts are rejected.
- `parameter(String... names)` and `noParameter(...)` inspect named parameters
  throughout the statement using SQM's `ParametersCollector`. Supply canonical
  names without `:`, `@`, or template prefixes. Names are case-sensitive.
  `parameterCount(int)` counts all named, anonymous, and ordinal placeholder
  occurrences; `positionalParameterCount(int)` counts only anonymous/ordinal ones.
  Repeated names/ordinals count repeatedly, not as distinct bindings. Strings and
  comments containing placeholder-like text do not count. Expected counts must be
  non-negative, and no supplied bind values are inspected.
- `structurallyEquals(expectedSql)` compares parsed SQM models. Whitespace,
  ordinary comments, and keyword casing do not affect equality. Identifier
  spelling and quoting, aliases, projection order, predicates, literals, and
  parameter names remain significant. This does not prove semantic equivalence.
  A failure renders the enclosing expected/actual SQL fragments using the selected
  dialect, for example `LIMIT 20 OFFSET 40` versus
  `LIMIT 10 OFFSET 40`. These are canonical SQL fragments, not excerpts of the original
  formatting. If SQM cannot render the fragment or its enclosing SQL, diagnostics fall
  back to the differing model path and values. Model paths are omitted when rendered
  SQL provides the context.

Table, schema, alias, and column-reference names compare case-insensitively when both identifiers are
unquoted. If either identifier is quoted, their values must match exactly.
This rule is the same for every dialect. Structural comparison continues to
preserve identifier spelling in all dialects.

Checks are combined with AND and all applicable failures are collected in declaration
order. Invalid actual SQL produces `PARSE_ERROR` diagnostics and skips model checks.
Invalid expected SQL or fragments throw `IllegalArgumentException` during evaluation
after actual SQL parses successfully. A parse failure skips requirement preparation
and evaluation. Null arguments are rejected. Unexpected errors
from custom checks propagate rather than becoming mismatches.

## Join sources, projection, and pagination

```java
var page = Expect.sql(POSTGRESQL)
    .select()
    .table("users u")
    .leftJoinTable("orders o")
    .exactProjection("u.id", "u.name AS display_name")
    .orderBy("u.created_at DESC", "u.id ASC")
    .limit(20)
    .offset(40)
    .parameter("tenantId")
    .noParameter("password")
    .parameterCount(1)
    .build();

page.assertMatches("""
    SELECT u.id, u.name AS display_name
    FROM users u LEFT JOIN orders o ON o.user_id = u.id
    WHERE u.tenant_id = :tenantId
    ORDER BY u.created_at DESC, u.id ASC
    LIMIT 20 OFFSET 40
    """);
```

Join-source checks describe presence/type rather than full join conditions. For
example, changing the join above to INNER fails `leftJoinTable("orders o")`, while
changing the ON predicate alone does not. Use `join(...)` when the condition is
part of the contract. Likewise, use `column(...)` for references anywhere and
`projection(...)` for the output list specifically.

### SQM 0.5.0 boundaries

Assert SQL inspects the SQM model without reparsing or interpreting SQL itself.
The current SQM parser attaches trailing ORDER BY/LIMIT/OFFSET to the last term
of some unparenthesized set queries rather than to their composite node. Our outer
ordering/pagination checks return `SQM_SCOPE_UNSUPPORTED` when the final term
carries such clauses; both positive and negative assertions fail instead of
guessing the scope. This conservative restriction also applies to intentionally
term-local clauses on the last term, since that distinction is lost in the model.
For composite-level assertions with this version, parenthesize the terms and put
the ordering/pagination after the composite query:

```sql
(SELECT id FROM users) UNION (SELECT id FROM orders)
ORDER BY id DESC LIMIT 20 OFFSET 40
```

This parser boundary needs an SQM fix; Assert SQL does not silently reinterpret
the final term's clauses. SQL Server's native `@id` expression syntax and some
keyword-based names such as `:limit` are also rejected by SQM 0.5.0. Parser-supported
canonical named syntax such as `:id` and `:pageSize` works. These inputs produce
parse diagnostics rather than successful negative assertions.

## Multiple requirements and alternatives

```java
var activeUsers = Expect.sql(POSTGRESQL)
    .table("users u", "orders o")
    .column("u.id", "o.user_id")
    .join("INNER JOIN orders o ON o.user_id = u.id")
    .where("u.active = true")
    .noColumn("password", "secret")
    .noTable("legacy_users", "archive")
    .build();

activeUsers.assertMatches("""
    SELECT u.id FROM users u
    INNER JOIN orders o ON o.user_id = u.id
    WHERE u.active = true
    """);

var archivedUsers = Expect.sql(POSTGRESQL)
    .table("archived_users")
    .column("id")
    .noJoin()
    .build();

Expect.or(activeUsers, archivedUsers)
    .assertMatches("SELECT id FROM archived_users");
```

Varargs have the same meaning as repeated calls: all positive arguments must
match, and all negative arguments must be absent. They are not OR lists. Every
fragment-taking varargs method rejects empty arrays and null elements. In
particular, `where("a = 1", "b = 2")` requires the same outer predicate to equal
both inputs; it does not construct `a = 1 AND b = 2`. Supply the complete predicate
as one fragment, or use separate built expectations with `Expect.or(...)` for
alternatives. `structurallyEquals` continues to take one complete expected statement.

`Expect.or(...)` accepts one or more built expectations, defensively copies the
alternatives, and evaluates them in order until one matches. Requirements inside
each branch remain AND requirements. If none matches, the result contains all
branch failures under paths such as `or[0].statement`. Each evaluated alternative
uses its own dialect and parse context. Exceptions from evaluated alternatives
propagate; alternatives after a successful one are skipped. Invalid SQL does not
match any built branch, including branches containing only negative checks.

## Custom checks using SQM

```java
import io.assertsql.Mismatch;
import io.sqm.core.SelectQuery;
import java.util.List;

var singleProjection = Expect.sql(POSTGRESQL)
    .satisfies(statement -> {
        if (statement instanceof SelectQuery query && query.items().size() == 1) {
            return List.of();
        }
        return List.of(new Mismatch(
            "SINGLE_PROJECTION", "statement.items", "Expected one SELECT projection."));
    })
    .build();

singleProjection.assertMatches("SELECT id FROM users");
```

Each SQL expectation evaluation parses actual SQL once (OR evaluates its branches
independently). Custom checks receive that same SQM
`Statement` instance and return an empty list for success or non-null diagnostics
for failure. Custom checks used in shared expectations must be thread-safe.

## Assert supplied parameter bindings

`ParameterizedSql` adds caller-supplied values to SQL inspection, using the same terminal
methods and assertion-framework-independent results. Binding checks are part of
core and do not execute SQL or require JDBC.

```java
import io.assertsql.Expect;
import io.assertsql.ParameterizedSql;
import java.util.Map;
import static io.sqm.core.dialect.SqlDialectId.POSTGRESQL;

var newUser = Expect.sql(POSTGRESQL)
    .as("new user arguments")
    .table("users")
    .parameterCount(2)
    .binding("tenantId", 42L)
    .binding("userName", "Ada")
    .matchAllParameters()
    .build();

var input = ParameterizedSql.named(
    "INSERT INTO users (tenant_id, name) VALUES (:tenantId, :userName)",
    Map.of("tenantId", 42L, "userName", "Ada")
);
newUser.assertMatches(input);
```

Individual value checks require that SQL references the slot and that its supplied
value matches; they permit unrelated extra or missing bindings. Add
`.matchAllParameters()` to require every actual SQL slot to be covered by a positive
`parameter(...)`, `binding(...)`, `positionalBinding(...)`, or `ordinalBinding(...)`
expectation. Uncovered SQL slots report `PARAMETER_UNEXPECTED`. Repeated names and
ordinals identify one slot; anonymous occurrences have separate positions.

The same method works with parameter-name expectations and String-only evaluation:

```java
Expect.sql(POSTGRESQL)
    .parameter("tenantId", "userName")
    .matchAllParameters()
    .build()
    .assertMatches("SELECT :tenantId, :userName");
```

An additional `:status` in this query would fail. Missing declared parameters still
fail their individual presence/value checks. Counts and negative checks do not
declare allowed slots. With no positive declarations, `.matchAllParameters()`
requires no parameters; `.parameterCount(0)` expresses that intent more clearly.
Its position in the fluent chain does not matter; build snapshots all declarations.

When explicit binding containers are supplied, an unscoped `.matchAllParameters()`
also requires bindings for every SQL slot and rejects unused bindings. Parameter
coverage itself needs no binding values. Value assertions and negative binding
checks still require them. Supplying `ParameterizedSql` alone does not activate checks;
existing occurrence-count and parameter-presence methods keep their meanings.

| Parameter kind | Input | Value assertion | Slot rule |
| --- | --- | --- | --- |
| Named, such as `:tenantId` | `ParameterizedSql.named(sql, map)` | `binding("tenantId", 42L)` | Canonical, case-sensitive name without prefix; repeated names share one slot |
| Anonymous `?` | `ParameterizedSql.positional(sql, list)` | `positionalBinding(1, 42L)` | One-based positions in SQM collector traversal; each anonymous occurrence has its own slot |
| Explicit ordinal, such as `$2` | `ParameterizedSql.ordinal(sql, map)` | `ordinalBinding(2, 42L)` | The index written in SQL; repeated indices share a slot and skipped indices need no binding |

For mixed SQL use `ParameterizedSql.of(sql, namedMap, positionalList, ordinalMap)`. The
three namespaces are independent: named and ordinal occurrences do not consume
anonymous positions. Repeated names/ordinals still count repeatedly in occurrence
checks; no expanded value list is inferred from those counts. Placeholder syntax
must be supported by the selected SQM parser.

Anonymous ordering follows SQM's model, **not a promise of driver bind order**.
For `SELECT ?, ?` or ordinary INSERT VALUES, the orders agree. For
`SELECT ? OFFSET ? ROWS FETCH NEXT ? ROWS ONLY`, SQM visits projection, limit,
then offset, so the input list is `[projectionValue, limitValue, offsetValue]`.
TOP with projection parameters and dialect pagination forms can also differ from
textual order. Use named/ordinal slots where available, or explicitly supply the
SQM order; Assert SQL does not reorder a driver/tool binding list automatically.
`BindingsTest` covers the OFFSET/FETCH boundary.

`noBinding(name)`, `noPositionalBinding(position)`, and `noOrdinalBinding(index)`
assert absence from the supplied containers, whether or not SQL references that
slot. A supplied null is present and therefore fails an absence check. Invalid
SQL fails with `PARSE_ERROR` before any binding check runs.

String-only evaluation and `ParameterizedSql.of(sql)` carry no binding information;
value checks and negative binding checks fail with `BINDINGS_UNAVAILABLE`.
Use an explicit empty container, such as `ParameterizedSql.named(sql, Map.of())`, when
you want to assert that nothing was supplied. Explicit nulls are supported in
maps/lists that allow them, for example `Collections.singletonMap("name", null)`;
they differ from absent keys or positions.

Values use Java `Objects.deepEquals`: arrays compare recursively by contents,
other objects use `equals`, and no numeric or JDBC conversion occurs. `42` differs
from `42L`; `BigDecimal("1.0")` differs from `BigDecimal("1.00")`. SQL types are
not inferred from supplied values. Input maps/lists are copied and exposed as
unmodifiable snapshots. Arrays and `Date` values are copied on input, expectation
declaration, and access; cyclic arrays are rejected. Other values are retained by
reference and must remain effectively immutable, including application objects
or collections used as individual binding values. This policy also applies to
expected values in reusable expectations.

Binding diagnostics identify the name, position, or ordinal and omit both expected
and supplied values. For example:

```text
- [BINDING_MISMATCH] bindings.named[userName]: Binding value differs from the expected value.
```

Scoped individual value checks use the selected query's parameters but retain
full-statement anonymous numbering; they never renumber a CTE or EXISTS body.
Negative binding checks inspect the full supplied container. In scope blocks,
`.matchAllParameters()` covers only parameters at the selected query level and
allows bindings belonging elsewhere in the input. Positive declarations in nested
blocks also contribute slot coverage to their ancestors. Root coverage includes
all query levels and validates supplied binding completeness for the entire input.
OR alternatives receive the same input and independently inspect their own parsed SQL.

[BindingsExampleTest](assert-sql-examples/src/test/java/io/assertsql/examples/BindingsExampleTest.java)
demonstrates named parameters from jOOQ's `getParams()` and anonymous values from
`getBindValues()`, with an unchanged SQL shape and incorrect values/order detected
without execution. SQL inspection cannot recover values from text; callers must
supply the values exposed by their query generator or capture tooling.

## Validate against a supplied catalog

Add the optional module when your tests need SQM schema validation. It includes
`assert-sql-core` transitively; applications using core alone do not acquire the
catalog or validator dependencies.

```xml
<dependency>
    <groupId>io.github.icher-g</groupId>
    <artifactId>assert-sql-validation</artifactId>
    <version>0.1.0-SNAPSHOT</version>
    <scope>test</scope>
</dependency>
```

Supply SQM's public catalog types directly. The catalog is explicit test data;
Assert SQL does not discover it from a database or ORM mappings.

```java
import io.assertsql.Expect;
import io.assertsql.validation.SchemaChecks;
import io.sqm.catalog.model.CatalogColumn;
import io.sqm.catalog.model.CatalogSchema;
import io.sqm.catalog.model.CatalogTable;
import io.sqm.catalog.model.CatalogType;
import static io.sqm.core.dialect.SqlDialectId.POSTGRESQL;

var schema = CatalogSchema.of(
    CatalogTable.of("app", "users", CatalogColumn.of("id", CatalogType.LONG), CatalogColumn.of("name", CatalogType.STRING))
);
var validUsers = Expect.sql(POSTGRESQL)
    .as("users schema contract")
    .satisfies(SchemaChecks.validAgainst(schema, POSTGRESQL))
    .table("app.users")
    .noSelectStar()
    .build();

validUsers.assertMatches("SELECT u.id, u.name FROM app.users u");
var invalid = validUsers.evaluate("SELECT u.missing FROM app.users u");
System.out.println(invalid.describe()); // Includes SQM's COLUMN_NOT_FOUND diagnostic.
```

`validAgainst(...)` returns a reusable `Check`. Validation runs only at evaluation,
on the original parsed statement, with SQM's name resolution, type checks, and
dialect rules. Invalid SQL produces `PARSE_ERROR` and skips validation. Use the
same dialect for parsing and validation: ANSI uses SQM's generic validator; the
other four dialects use their SQM extensions and default dialect versions.

Each SQM problem retains its code, message, available clause path, and reporting
order in `Match`. SQM 0.5.0 exposes no severity or warning field: every reported
problem fails the check. Unsupported dialect identifiers are rejected when creating
the check. Custom `DialectQuery` models and MERGE statements unsupported by SQM's
configured dialect capabilities produce `VALIDATION_UNSUPPORTED`; native SQM
dialect feature diagnostics retain their original codes.

Attach validation at the root to preserve the full CTE and correlated-reference
context. Inside `.outer(...)`, `.cte(...)`, `.derived(...)`, or `.exists(...)`, it
validates only the selected body as a standalone statement, without enclosing
bindings. SQM supports query and DML validation, including the CTE/subquery forms
covered by the tests; its coverage and limitations apply here. In particular,
SQM 0.5.0 can accept an unknown derived-table output column such as
`SELECT q.missing FROM (SELECT id FROM app.users) q`. A successful check means SQM
reported no problems; it does not prove runtime results, constraints, or plans.

`CatalogSchema`, `CatalogTable`, and their contents are immutable; SQM copies
caller-owned collections during construction. The check retains the supplied
catalog reference and creates fresh validation state for each evaluation, so it
can be reused concurrently. Create a new catalog/check for a different schema.
SQM's permissive catalogs, such as `CatalogSchema.allowEverything()`, retain
their permissive behavior and cannot verify table/column existence.

[CatalogValidationExampleTest](assert-sql-examples/src/test/java/io/assertsql/examples/CatalogValidationExampleTest.java)
validates actual jOOQ-generated SQL with a CTE and correlated EXISTS using an
in-memory catalog, including a missing-column failure, without a database.

## Build

Requires JDK 21 or later and Maven 3.9 or later.

```shell
mvn verify
```

The parent manages dependency and build plugin versions. `assert-sql-core`
provides the structural API in `io.assertsql`; optional `assert-sql-validation`
adds `io.assertsql.validation.SchemaChecks`. Both use Maven group
`io.github.icher-g`. JUnit Jupiter is used only for tests.

SQM is an external dependency (`io.github.icher-g:sqm-core:0.5.0`), resolved from
Maven Central. No extra repository configuration, GitHub credentials, or local
SQM checkout is needed. Its version is managed by the parent's `sqm.version` property.
